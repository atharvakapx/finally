<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| App → SQLite file | All DB writes cross from process memory to the bind-mounted file. |
| Env → DB path | `DB_PATH` env var controls where the DB file is created. |
| Concurrent threads → SQLite | Future trade endpoints (Phase 2) will fire concurrent writes; `BEGIN IMMEDIATE` serializes them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | `DB_PATH` env points outside intended directory | accept | Single-user demo; PLAN.md §11 documents `/app/db/finally.db` as the canonical path. No filesystem isolation expected in v1. |
| T-02-02 | Repudiation | Trades / chat_messages have no audit chain | mitigate | All write tables include `created_at`/`executed_at` ISO timestamps; trades table is append-only by design (no UPDATE/DELETE in code paths). |
| T-02-03 | Tampering | Race condition on `cash_balance` (double-spend) | mitigate | `get_db_immediate()` issues `BEGIN IMMEDIATE` which acquires SQLite's write lock immediately, serializing concurrent writers (DB-05). Verified by `test_get_db_immediate_serializes_writers`. |
| T-02-04 | Information Disclosure | DB file readable by anyone with host access | accept | Bind-mounted file owned by container user; v1 is single-user demo per PLAN.md scope. |
| T-02-05 | Denial of Service | Idempotent `init_db()` on every boot — slow startup with large DB | accept | `CREATE TABLE IF NOT EXISTS` and `INSERT OR IGNORE` are O(1) when rows exist; negligible cost. |
| T-02-06 | Tampering | SQL injection via unparameterized queries | mitigate | All `INSERT`/`UPDATE` in `db.py` use parameterized queries (`?` placeholders). No string-formatted SQL allowed. Acceptance criterion verifies `INSERT OR IGNORE INTO users_profile (...) VALUES (?, ?, ?)` shape. |
</threat_model>
